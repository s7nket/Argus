# ARGUS scorer evaluation

Answers one question: **is the judge any good, and is the fine-tuned 4B judge better than the alternatives?**

Without this you cannot tell. The scorer can agree with humans and still be
useless if every score lands in a 1.5-point band, and it can look consistent
while simply reacting to which chair a debater sits in.

## Workflow

```bash
python -m eval.capture --rounds 2      # record debates from the running backend
python -m eval.label                   # label them by hand (run in a real terminal)
python -m eval.evaluate                # compare scorers against your labels
```

Aim for **~30 labelled rounds** before trusting any number. Below 20 the harness
prints a warning and the figures are directional at best.

## The three arms

| arm | what it is |
|---|---|
| `legacy` | the original rubric — three undefined criteria, no scale anchors, PRO/CON labels visible, one pass |
| `blind` | current pipeline — extraction before scoring, anchored 0-10 scale, two label-swapped passes, evidence caps |
| `ft` | the fine-tuned 4B scorer on Kaggle via `FT_JUDGE_URL`, raw and unaudited |

Run a subset with `--arms blind ft`.

## Reading the table

| column | meaning |
|---|---|
| `agree` | fraction of rounds where the scorer picked the same winner you did |
| `kappa` | that agreement corrected for chance — near 0 means no better than guessing the majority outcome |
| `corr` | correlation between the scorer's margin and your verdict direction |
| `compress` | fraction of scores inside the 7.0-8.5 band. **High is bad** — the scorer is not discriminating |
| `spread` | standard deviation of all scores. Low means the same thing as high compression |
| `pro rate` | how often the scorer picks PRO. Compare to the `gold` row |
| `drift` | mean gap between the two label-swapped passes (blind arm only) |

Failure signatures worth knowing:

- **compression high, agreement high** — the scorer picks winners correctly but its
  margins are noise. A 0.2-point "win" is a coin flip.
- **drift above ~0.5** — the scorer is responding to the labels, not the arguments.
  Two passes over identical text should not disagree much.
- **pro rate far from the gold pro rate** — position bias. Label-swapping does not
  fix this; PRO opens and CON closes every sub-round, so the last-word advantage
  is structural. To measure it, capture the same topics with the roles reversed.
- **kappa near 0 with high agreement** — one outcome dominates your label set and
  the scorer is riding the base rate.

## Cost

Each `blind` round costs two `llama-3.3-70b-versatile` calls; `legacy` and `ft`
cost one each. A 30-round three-arm run is ~120 judge calls and **will exhaust the
Groq free tier** (100k tokens/day). Options:

- run one arm per day, or use `--limit`
- `--concurrency 2` if you hit per-minute limits (the harness already backs off and retries)
- set `BLIND_PASSES=1` in `backend/.env` to halve production judge cost, at the
  price of losing the drift signal

The token ceiling is the strongest practical argument for getting the FT judge
working: a local 4B removes the 70b from round scoring entirely.

## Retraining note

If the 4B was fine-tuned on labels generated by an LLM judge using the `legacy`
rubric, it has learned to reproduce that rubric's score compression — check its
`compress` column first. In that case the fix is to regenerate training labels
with the anchored rubric in `agents/judge_agent.py` and retrain, or to repurpose
the model for fallacy classification and evidence-span tagging, where a small
fine-tune genuinely beats a large general model.

## Files

| file | role |
|---|---|
| `dataset.py` | `RoundRecord` and JSONL load/save. Data lives in `eval/data/rounds.jsonl` |
| `capture.py` | drives the WebSocket, records rounds |
| `label.py` | interactive labelling. Shows no model opinion — a suggestion would anchor you to the scorer you are measuring |
| `evaluate.py` | runs the arms, prints the report |
| `metrics.py` | agreement, Cohen's kappa, Pearson, histogram, compression. No third-party deps |
